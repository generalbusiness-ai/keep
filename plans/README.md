## Findings considered and rejected

These were investigated and **dropped during vetting** — recorded so they aren't
re-audited:

- **"Blind POST retry double-writes on 401" (`mcp.py:94-106`)** — FALSE POSITIVE.
  A 401 means the daemon *rejected* the request (it never executed); re-resolving
  the port and retrying is safe, not a duplicate write.
- **"Bearer token stored in memory" / "api_url scheme unvalidated" (`remote.py`)**
  — NOT FINDINGS. The constructor already calls `validate_remote_api_url`; holding
  a token on an HTTP client is standard.
- **"Daemon token file world-readable"** — FALSE POSITIVE. Written with
  `mode=0o600` (`console_support.py:1760`).
- **request_id operator docs (prior N004), prior N001/N002/N003, F030, F036,
  F037** — already RESOLVED in the ~70 commits since the last tech-debt audit
  (mostly commit `54586b9`). Verified against the working tree; not re-planned.
- **Daemon 400 echoes Pydantic `errors()` (#6 above)** — genuine minor info-leak
  but the daemon is loopback-only with an auth token, so impact is low; not
  selected for a plan. If the daemon ever gains a non-loopback bind mode, revisit
  (alongside the existing F022/F044 rate-limit/CORS items).
- **cli_app.py / console_support.py / test_data_export.py growth** — real debt
  (cli_app.py grew +831 LOC to 3258 from the remote-backend feature work; see
  prior audit F003/F041) but L-effort and HIGH-risk to refactor; low leverage
  right now. Left on the record, not planned.
